### R04 · 기본 단가 정정 내역 + 6.1 실제 실험 기준

모든 값은 **1,000토큰당 USD**다. 최초 단위 오류 수정 이력과 실제 6.1 실험에 맞출 단가를 함께 표시한다.

| 대상 | 최초 잘못된 기본값 | mini 단위 정정값 · 현재 소스 기본 | 6.1 실험용 환산값 |
|---|---|---|---|
| 생성 입력 / 출력 | $0.15 / $0.60 | $0.00015 / $0.00060 | **$0.002 / $0.010** |
| Guard 입력 / 출력 | $0.15 / $0.60 | $0.00015 / $0.00060 | **Guard도 6.1이면 $0.002 / $0.010** |

`gpt-6.1-sol` Standard 공식 단가는 100만 토큰당 입력 $2·출력 $10이다. 기존 계산식이 1,000으로 나누므로 위처럼 환산한다. [공식 모델·요금](https://developers.openai.com/api/docs/models/gpt-6.1-sol).

**이 표의 갱신은 실행 서버의 모델·단가 변경이 아니다.** 현재 Java 생성·Guard 장부 기본값과 NeMo config는 mini다. 실제 생성/NeMo 모델이 6.1인지 확인하고 두 경로 모두 적용 요금을 맞춰야 한다. Guard 장부 모델 이름만 바꿔도 NeMo 모델이 바뀌지는 않는다. 실제 프로젝트 권한·환경변수·비밀 키 설정은 R01/R03/R04-3에 남아 있다.

3회 비용은 [최신 상세표](GPT61_THREE_RUN_COST_ESTIMATE_2026-10-22.md) 기준 **생성12회 + Guard24단계 = LLM36회 가정, 네이버 변협 대상/일반 검색 총6회**, 최종 결과/설명 최대9개다. Guard 내부 다중 호출·비가시 추론량은 실측해야 한다. 이전 $0.09~$0.39는 Guard 출력 상단512 가정이며, 최신 표는 128~1,024 가정으로 약 $0.10~$0.51을 표시한다. 무료 오픈 API 계약 조건의 네이버 검색 요금·변협 직접 호출 없음도 상세표에 구분했다.

공급자 측 알림은 요청을 중단하지 않는다. OpenAI의 hard spend limit도 추적된 지출을 기준으로 적용되며 즉시 반영이 아니어서 소액 초과가 가능하다. 학원 조직·프로젝트에 실제 어떤 한도가 적용됐는지는 R02에서 별도 확인한다. [공식 지출 제한 안내](https://developers.openai.com/api/docs/guides/spend-limits).

### R06/R07 · 첫 실험에서 특히 헷갈리기 쉬운 범위

- 사건 본문 기본 한도는 **분류·등록·일반 Chat/SSE 모두 100자**, 비용 길이 게이트도 1×100자다. 기존 10자 설정은 더 엄격한 차단 기준이었으며 10자로 나누는 처리는 없다. 가상 질문으로 첫 경로를 확인하고 기존 환경변수가 이전 10/2000/256 등의 설정을 덮어쓰고 있는지 점검한다.
- 생성 프롬프트에는 사용자 문장 외에 시스템 프롬프트·Guard 수정 내용 등이 포함된다. 사용자의 입력만으로 1회 비용을 계산하지 않는다.
- 일반 정상 경로는 입력 Guard → 생성 → 출력 Guard의 비용을 고려한다. Guard의 내부 LLM 호출 횟수와 토큰 상한은 Java 예약값만으로 증명되지 않는다.
- P03 기본 결과 3개라면 검색문 생성 1회 + 결과별 설명 최대 3회, 각 생성 전후 Guard 검사까지 이어질 수 있다. 이는 **생성·설명 4회 + Guard 검사 최대 8단계**의 계산 예이며, NeMo 내부가 단계당 LLM 1회라는 보장은 아니다.
- P03 실패 후 설명만 다시 생성하더라도 새 유료 호출이 발생할 수 있다. 조회 폴링 GET과 실행/재생성 POST를 구분한다.
- 예약·한도 판정은 추정 토큰을 사용한다. 실제 usage가 추정을 넘으면 정산 후 장부가 한도를 초과할 수 있어 로컬 예산만으로 공급자 청구의 절대 상한을 보장하지 못한다.

## 3. 준비 완료 후 소량 호출로 남은 확인

R01~R10을 확인한 뒤 아래 항목을 하나씩 진행한다. 전부를 동시에 실행하지 않는다. 이전 단계가 실패하면 추가 유료 재시도 전에 원인을 확인한다.

- [ ] **L04 · 이번 시연의 첫 정상 호출 — P03 결과 1개:** R01~R10 및 네이버 설정 확인 후, 별도 실험 설정에서 결과를 1개로 제한하여 검색문→외부 검색→저장→설명 흐름을 검증한다. 동일 ID 중복 실행의 호출 수·단계별 usage·예약 종료·공급자 비용을 확인한 뒤 결과 3개 및 시연 3회로 늘린다. L01/L02 유료 실험은 P03의 선행 필수 단계가 아니다. 화면02~04 성공은 유료 LLM 성공 증거가 아니다.
- [ ] **L01 · 별도 일반 Chat 1건:** 필요 시 개인정보 없는 짧은 법률 질문으로 S01 정상 응답·응답 모델·usage 확인. 입력 Guard/answer/출력 Guard의 비용 증가, 예약 종료, 공급자 사용량을 대조한다. 이번 P03 3회 계산에는 이 호출을 넣지 않았다.
- [ ] **L02 · 별도 SSE 정상 1건:** SSE 사용 검증을 별도로 진행할 때 S02의 terminal 이벤트, usage 출처, 마스킹, 단계별 비용과 예약 종료를 대조한다. P03 선행 유료 호출로 강제하지 않는다.
- [ ] **L03 · 별도 SSE 중단 1건:** SSE 실험 예산을 별도로 정한 뒤 실제 공급자의 연결 종료·usage 미확인 시 동작을 확인한다. 로컬 취소 성공을 공급자 과금 취소로 판정하지 않는다. timeout 등 장애는 우선 모의 재현하고 공급자 차이가 있는 부분만 추가 확인한다.

공급자 사용량 화면의 집계 지연과 프로젝트 공유 사용량을 고려한다. 로컬 `REPORTED`는 토큰 수가 보고됐다는 의미이지 학원 청구 금액이 확정됐다는 의미가 아니다. 보고된 usage가 없는 정산은 `ESTIMATED`로 남기고 확인 완료 체크를 하지 않는다.

## 4. 서비스 확대 전 별도 보완

- [ ] 재시작·여러 인스턴스·외부 도구 사용을 아우르는 영속 비용 원장/공급자 청구 대사. 현재 메모리 장부를 영구 월간 지출로 해석하지 않기.
- [ ] Chat/SSE의 서버 강제 동시 실행 수·요청 빈도·사용자별 비용 통제와 요청 중복 방지. 세션 ID 변경은 사용자별 누적 한도와 같지 않다.
- [ ] 선택 모델 tokenizer·실제 usage 대조 및 Guard 내부 다중 호출·출력 상한 확인. 입력의 UTF-8 바이트 기반 보수 예약·Chat 형식 여유는 구현했으나 공급자 청구 상한을 보장하지 않는다.
- [ ] 외부 접속 시 개발용 계정/JWT 기본 설정 교체와 기존 문의·운영 API의 인가 보완. 로컬 단독 실험 조건과 운영 공개 조건을 구분.

위 항목 전체의 신규 구현을 첫 로컬 1건 실험과 묶어 요구하는 것은 아니다. 다만 현재 한계가 있는 상태에서는 R02/R07/R09/R10의 공급자 한도·단독 실행·수동 제한·중단 절차를 충족해야 한다.
