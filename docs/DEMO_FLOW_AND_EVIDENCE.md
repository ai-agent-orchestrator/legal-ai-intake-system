# 시연 흐름과 최소 실행 근거

2026-10-19 기준. 기능 매핑에 시간을 투자하고, 의미 있는 실행 확인을 시연에 재사용한다. 기존 193페이지 API Flow PDF는 유지하며 이 문서는 촬영 범위와 완료 근거만 기록한다. 아래 표는 실행 계획이며 촬영·검증 완료 기록이 아니다.

**작업 우선순위:** 제출 필수 산출물인 시연영상 완성을 우선한다. 매핑 → 핵심 흐름 구현 → 필요한 최소 연결 확인 → 촬영 순서로 진행한다. Postman은 촬영 전 연결 확인·오류 재현용 보조 도구이며, 전수 실행·별도 캡처 묶음·반복 수동 검증에 시간을 배정하지 않는다. 기존 4+4 요청은 참고 경로이며 별도 필수 할당량이 아니다. 같은 환경·조건에서 이미 실행 근거가 있거나 시연으로 확인한 내용은 중복 실험하지 않는다. 시연을 막는 실패와 변경한 기능의 미검증 조건을 우선 확인한다.

## 1. 최종 시연 범위

| 장면 | API·필수 요구사항 | 보여줄 연결 | 남길 근거 |
|---|---|---|---|
| 1. React–Spring Boot 연동·CORS | REQ-01·02 / R01·R02·R06 | Previewer 화면 → 실제 HTTP 요청 → LegalProcedureController → S.조회·응답 메서드 → 화면 갱신 | 브라우저 Network의 URL·응답·화면 결과. preflight가 필요한 요청은 OPTIONS·허용 헤더까지 확인 |
| 2. 문의 등록·목록·상세·검토 | C01·P01·C03·C09·C05·C10·C11 | 로그인 → 문의 등록 → 목록에서 ID 선택 → 상세 → 상태 변경·메모 → 상세 재조회 | 문의 PK 유지, 변경된 상태·새 메모, DB 행과 응답의 연결. 실제 MySQL을 사용하면 재시작 후 유지 확인 |
| 3. 검색 준비 → 실제 실행 → 결과 | C06 → P03 → C07, 필요 시 P02 | 검색 요청 생성 → 별도 실행 요청 → LLM 라우팅·검색 → 결과 저장 → 상세 조회 | intakeId와 searchRequestId 구분, 실제 외부 호출 근거, 저장 결과·출처·상태. P03은 현재 미구현이며 구현 후 촬영 |
| 4. LLM 질문·서버 비동기·안전 응답 | REQ-03·04 / S01·S02 | AiController → S.chat / AiStreamingService.stream → NeMo·LLM → 출력 검사·Privacy → JSON / SSE | 실제 외부 서비스 연결, 정상 답변, 차단·오류 대표 경우. S02는 전체 답변 검사·마스킹 후 전송 |
| 5. 지연 통제·동시 요청·관측 | REQ-05 / S01·S02·C16 | 비동기 호출·웹 요청 가상 스레드·사전 차단·출력 상한·타임아웃·시간 측정의 코드 위치 연결 | isVirtual()·스레드 로그 또는 JFR, S01 단계별 Timer, C16 지표. 개선 수치를 주장할 경우 동일 조건의 처리량·P50/P95·오류율 비교 |
| 6. 실제 LLM 호출의 Cost Control | P03 구현 후 + S01·S02 / C16 | 허용 요청의 예약 → 실제 호출 → 사용량 보고/추정 정산, 예산 부족 요청의 호출 전 차단 | 호출 전후 사용액·예약액, usageAvailable·costSource 등 실제 응답 계약, 차단 사유와 외부 호출 미발생 근거 |

장면 3과 6은 같은 실행의 결과·비용 근거를 재사용할 수 있다. 장면 4와 5도 같은 질문의 응답·시간 지표를 연결한다. 최종 결과만 보여주기보다 요청 → Controller → Service → DB·Client → 응답을 짧게 짚는다. 새 React 화면 연결 전에는 Postman·코드·DB로 시연하고, 화면 시연 완료와 구분한다.

## 2. P03 구현 후 반드시 연결할 흐름

아래는 후속 구현의 완료 기준이다. 실제 Controller·Service·상태명·응답 DTO는 구현 후 API 기능서와 대조한다.

```text
C06: 문의의 검색 요청 준비 기록 생성
→ searchRequestId 확보
→ P03: 해당 검색 요청의 실제 실행을 별도로 요청
  → 담당 Controller → 담당 Service
  → 실제 호출별 입력·출처·권한 정책 적용
  → LLM / 유료 외부 단계의 비용 예약·예산 검사
     ├─ 예산 부족: 해당 외부 호출 전 차단·사유 기록
     └─ 허용: 실제 LLM 라우팅·외부 검색 실행
        → 보고 사용량 또는 미보고 추정 정산
        → 출력·출처 검증 → 검색 결과·실행 상태 저장
→ C07: 저장된 실행 결과 조회
→ C16: 대응하는 호출·비용·예약액 확인
```

- C06은 현재 PREVIEW_READY 준비 기록을 만들며 실제 검색·LLM을 실행하지 않는다.
- C08은 호출자가 제공한 결과 스냅샷을 저장한다. 이 성공을 P03의 실제 검색 성공 근거로 사용하지 않는다.
- 현재 S01~S04 비용 통제가 P03에 자동 적용되는 것은 아니다. P03의 실제 외부 호출 경로에 예약·정산·차단을 명시적으로 연결해야 한다.
- LLM 라우팅 호출 성공과 외부 검색 성공, 결과 DB 저장 성공을 각각 확인한다. fallback이나 고정 응답을 실제 LLM 성공으로 기록하지 않는다.
- 기본 0.3달러는 세션 예산이다. 요청마다 새로 부여되는 예산으로 설명하지 않는다. P03의 세션 연결·공통 예산 포함 범위는 구현 계약에서 확정한다.
- 비용은 보고 사용량과 추정 사용량을 구분한다. 사용량 미보고·외부 장애·중단 시 예약의 중복 정산이나 미해제가 없는지도 확인한다.
- 예산 차단은 낮춘 실험 예산 또는 고정 fixture로 재현할 수 있다. 실제 서비스 연결 확인 장면과 모의 차단 검증의 근거를 구분한다.

## 3. 필수 요구사항과 시연 근거의 구분

| 구분 | 완료 근거 |
|---|---|
| Spring Boot–React·CORS | 실제 브라우저에서 화면·Network 확인. Postman만으로 브라우저 CORS 완료를 판단하지 않음 |
| 비동기 LLM·SSE | S02의 sendAsync·콜백 코드와 실제 이벤트 수신·종료. 모든 처리 단계가 병렬이라는 의미는 아님 |
| 가상 스레드 | 공통 설정과 실제 요청·콜백 실행 스레드 확인. S02 콜백 전체가 가상 스레드라고 가정하지 않음 |
| 지연 통제 구현 | 사전 차단·출력 상한·타임아웃·관측의 코드와 실제 결과 |
| 성능 개선 효과 | 동일 조건의 반복·동시 요청 비교. 설정·코드 존재만으로 개선율을 제시하지 않음 |
| 실제 LLM·Cost Control | 실제 호출·사용량 근거와 예약·정산·차단 근거를 함께 제시. 실제 청구 대사와는 구분 |

현재 학습·연결 확인의 최소 4+4 요청은 [Postman 최소 실행 색인](POSTMAN_API_CHECKLIST_INDEX.md)에 유지한다. P03 구현 후에는 위 실행·비용 경로를 추가해야 최종 시연 범위가 충족된다. 자동 테스트로 확인한 실패 조건은 같은 조건을 전부 수동 재실행하지 않고, 실행 근거를 연결한다.

## 4. 촬영 때 남길 최소 기록

`장면 → API 번호·ID → Controller·Service → DB·Client → 기대 결과·실제 결과 → 비용·시간 근거 → 현재 검증 상태`

상태는 계획 / 구현 / 자동 검증 / 실제 환경 검증 / 촬영 완료로 구분한다. 기존 매핑을 그대로 활용하고, 촬영을 위해 별도 장문의 학습 문서를 늘리지 않는다.
