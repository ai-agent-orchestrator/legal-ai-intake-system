# 마케팅 전환·이탈 분석 구현 대조 — 2026-10-25

## 결론

화면10의 기본 집계는 구현돼 있다. 하지만 계획에 기재한 전환율·이탈 지점 분석, 이번에 요청한 상담 후 수임 전환 분석은 구현돼 있지 않다. 기존의 화면/API 정상 동작 검수는 이 분석 기능의 완료를 의미하지 않는다.

**후속 반영:** API·DB를 유지한 화면10 ‘시연 분석’ 모드를 추가했다. 가상 문의 40건으로 퍼널·상담 후 수임률·미수임 사유를 계산한다. 아래 미구현 판정은 **실제 고객 데이터 분석**에 관한 것이며 그대로 유효하다. 구현·검수 내역은 [마케팅 시연 분석 검수](MARKETING_DEMO_REVIEW_2026-10-25.md) 참고.

## 계획과 현재 구현

| 항목 | 현재 상태 | 근거 / 부족한 내용 |
|---|---|---|
| 문의·검색 건수 | 구현 | C13 `GET /api/admin/dashboard/marketing-funnel` |
| 검색을 요청한 고유 문의 수 | 구현 | 동일 문의의 여러 검색 요청과 구분하여 집계 |
| 현재 상담 준비 건수 | 구현 | 현재 상태가 `CONSULTATION_READY`인 문의 수 |
| 사건 유형·희망 다음 단계·지역 분포 | 구현 | 저장된 문의 기준 건수·구성비 |
| 방문→작성→접수→안내→검색 여정 자동 수집 | 미완성 | P06 이벤트 저장 API는 있지만 React 제품 소스에 호출 연결이 없음. 검수 스크립트의 직접 이벤트 입력은 자동 수집 구현이 아님 |
| 단계별 전환율·이탈 지점 | 미구현 | 응답은 `dropOffMeasured=false`. 화면에서도 계산하지 않는다고 명시 |
| 상담 예약·상담 완료 | 미구현 | 문의 상태/행동 이벤트에 해당 기록 없음 |
| 상담 완료→수임·계약 전환 및 미전환 사유 | 미구현 | 결과·결과 시각·사유를 저장하거나 집계하는 계약 없음 |
| 기간·동일 유입 집단 기준 비교 | 미구현 | 현재 DB 전체 자료를 집계하며 기간별 전환 분모를 구성하지 않음 |

README의 `Boards And Dashboards`에는 상담 준비 완료율·중도 이탈을, `Dashboard Enhancement`에는 문의 전환율·이탈 지점 분석을 목표로 기재했다. 현재 구현 설명의 ‘마케팅 기본 집계’와 목표 범위 사이에 차이가 있다. 상담 후 수임 전환은 이번 요청에 맞춰 추가로 명확히 정의해야 할 범위다.

## 실행 응답 확인

- 확인 대상: 격리된 로컬 시연 서버 `http://127.0.0.1:18080`의 C13. 실제 운영 데이터에 대한 판정이 아니다.
- 관리자 로그인 후 조회 성공. LLM·네이버 호출 없이 확인했다. OpenAI 설정은 변경하지 않았다.
- 원본 집계 응답: `output/marketing-gap-2026-10-25/current-c13.json` (토큰·사건 원문 없음).

| 반환 항목 | 값 |
|---|---:|
| 접수 문의 | 13 |
| 검색 요청 | 6 |
| 검색 요청한 고유 문의 | 6 |
| 현재 상담 준비 | 5 |
| VISIT / INTAKE_STARTED / SUMMARY_VIEWED | 각각 0 |
| dropOffMeasured | false |
| measurementBasis | ALL_RECORDS_IN_CURRENT_DATABASE |

방문·작성·안내 이벤트가 0인 것은 이 서버에서 해당 이벤트가 기록되지 않았다는 뜻이다. 실제 방문자가 없거나 모두 이탈했다는 뜻으로 해석하면 안 된다.

## 지금 건수로 전환율을 만들 수 없는 이유

1. 이벤트 횟수, 저장 문의 수, 고유 문의 수, 현재 상태 수가 섞여 있다. 같은 사람·문의의 순차 진행을 보장하지 않는다.
2. `CONSULTATION_READY`는 상담 준비 상태이며 상담 완료·수임이 아니다. 이후 다른 상태로 변경하면 현재 상담 준비 건수는 줄어 과거 진행 실적을 잃는다.
3. 동일 `eventId` 재전송 방지는 있지만, 새 ID로 반복 방문한 것을 동일 여정 단계의 고유 도달 1건으로 처리하는 집계는 없다.
4. 아직 응답을 기다리는 문의를 확정 이탈로 볼 수 없다. 집계 대상 기간과 관찰 기간, 진행 중/미전환/이탈의 구분이 필요하다.

## 최소 보완안 — 구현 전 제안

화면10 안에서 **문의 진행 현황**과 **상담 후 수임 성과**를 구분해 보여주는 방향을 권장한다.

- [ ] **여정 자동 기록:** 방문·작성 시작·접수·안내·검색을 연결할 식별자와 발생 시각 정의. 접수 전 여정과 `intakeId` 연결. 새로고침·재전송·다중 탭 중복을 구분하고 서버 집계도 고유 도달 기준으로 처리.
- [ ] **상담 결과 입력:** 담당 변호사가 상담 예약/완료, 수임/미수임/검토 중, 결과 시각과 선택형 미수임 사유를 기록. 운영자는 전체 집계를 보고 수정 권한은 서버에서 제한. 상태 전이 이력을 남겨 현재 상태와 구분.
- [ ] **전환 계산:** 같은 기간에 유입된 문의 집단을 기준으로 단계별 고유 도달 수와 다음 단계 도달률 표시. 상담 후 수임률은 ‘상담 완료한 동일 집단 중 수임한 문의 / 상담 완료 문의’로 정의하고 진행 중도 별도 표시. 분모 0은 `—`.
- [ ] **이탈 해석:** 단계 미도달과 확정 이탈을 구분. 관찰 기간이 지난 미도달 건, 명시적 미수임 사유, 아직 진행 중인 건을 나눠 표시. 단순 건수 차이로 이탈 원인을 단정하지 않음.
- [ ] **운영 화면:** 기간, 접수→상담→수임 퍼널, 단계별 감소 건수/비율, 가장 감소가 큰 구간, 미수임 사유 순위. 사건 원문·연락처는 분석 응답에 포함하지 않음.
- [ ] **완료 검증:** 새로고침/중복 접수 미중복, 이전 상태 이력 유지, 기간 경계, 분모 0, 진행 중/미수임 구분, 권한, API와 화면 숫자 대조. 고정된 시나리오 데이터의 기대 전환율과 비교.
