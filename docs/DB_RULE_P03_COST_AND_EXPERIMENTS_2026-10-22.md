**후속 비용표:** 3줄·100자 입력×3회, 생성/Guard 모두 6.1 Standard·결과3개 가정의 최신 계획 범위는 **약 $0.10~$0.51, 중간 가정 약 $0.26**다. [R04 환산·Guard 합산·변협/네이버 요청 상세](GPT61_THREE_RUN_COST_ESTIMATE_2026-10-22.md). 아래 2절은 이전 Guard 출력64~512 가정의 계산 이력이며 실측값이 아니다. 최신 표는 출력128~1,024 가정을 사용한다. 실행 모델·단가 기본값은 아직 mini다.

`[x]`는 명시한 소스/로컬 모의 검사 범위에서 확인한 항목이다. `[ ]`는 남은 확인이며, 실제 공급자 실험은 준비 항목 완료 후 순서대로 진행한다. 장애·경합·날짜 변경은 우선 모의 서버로 재현하고, 공급자 차이가 있는 부분만 별도로 소량 확인한다. 모든 항목을 유료로 한 번씩 호출하라는 뜻은 아니다.

## 1. 유지할 흐름과 외부로 보내는 내용

```text
화면02: C02 분류 미리보기 ─ 규칙 기반, 미저장
   ↓
화면03: C03 문의·검색 조건 DB 저장 ─ intakeId / conditionId
   ↓
화면04: C04 간단 안내·C05 문의 조회·Reference 절차 ─ 규칙·템플릿·DB
   ↓
화면05: C06 검색 요청 저장 ─ searchRequestId
   ↓ 명시적으로 P03 실행
안전한 검색 조건 → 입력 Guard → LLM 검색문 → 출력 Guard
   ↓
네이버 2회 검색: 변협 도메인 지정 + 일반 웹 → 중복 제거·최대 3개 저장
   ↓ 결과별
조건 + 제목·요약 → 입력 Guard → LLM 관련성 설명 → 출력 Guard
   ↓
C07/P02 조회: 같은 요청 ID로 저장된 결과·설명·상태 표시
```

- 화면02~04를 LLM 사건 정리로 바꾸려면 별도 호출·응답 연결이 필요하다. 이번에는 추가하지 않으므로 해당 단계의 **LLM 토큰 비용은 $0**이다. DB·서버 운영비까지 $0이라는 뜻은 아니다.
- P03 `SearchLlmService.safeConditions`는 법률 분야·분쟁 유형·광역 지역·허용된 선호 조건만 사용한다. 사건 원문, 의뢰인/상대방 이름·전화번호·상세 주소, 자유 입력 검색 목적, 문의/검색 ID를 그대로 프롬프트에 넣지 않는다. 설명에는 외부 검색 결과의 제목·요약도 들어간다.
- 원문 외부 전송을 줄이는 설계다. **DB에 저장한다는 사실만으로 개인정보 보호가 완성되지는 않는다.** 조회 인가·마스킹·로그·보관 정책과 실제 외부 전송 내용은 아래에서 확인한다.
- 변협 직접 API를 연동한 방식은 아니다. **네이버에서 `site:klaw.or.kr`로 공개 페이지를 찾고 일반 검색 결과와 섞는 방식**이다. 현재 자격·경력이나 변호사 추천 순위의 보증으로 표시하지 않는다.
- 이 흐름은 일반 Chat/SSE(S01/S02)를 호출하지 않는다. 별도 Chat/SSE 실험 비용을 아래 3회 비용에 더해 놓지 않았다.

## 2. 이전 gpt-6.1-sol 토큰 가정의 비용 비교 기록

2026-10-22 확인한 공식 Standard 텍스트 단가는 **입력 $2 / 출력 $10, 각각 100만 토큰당**이다. 아래 계산은 생성과 Guard가 모두 같은 단가를 쓴다고 가정한다. 다른 Guard 모델이면 그 모델 단가로 다시 계산한다. [공식 모델·단가](https://developers.openai.com/api/docs/models/gpt-6.1-sol).

```text
USD = (전체 입력 토큰 × 2 + 전체 출력 토큰 × 10) / 1,000,000
```

토큰 범위는 실측치가 아닌 **시연 계획용 가정**이다. 시스템 지시문·조건 JSON·검색 결과 제목/요약·Guard 프롬프트를 입력에 포함한다. 출력은 보이는 문장뿐 아니라 과금되는 추론·형식 토큰까지 포함한다고 가정한다. 30자 입력에만 요금을 곱한 계산이 아니다.

| 호출 종류 | 검색 1회당 호출 수 가정 | 호출 1개 입력 토큰 가정 | 호출 1개 출력 토큰 가정 |
|---|---:|---:|---:|
| 검색문 구성 | 1 | 500~1,500 | 128~512 |
| 결과 설명 | 3 | 800~2,500 | 256~1,024 |
| 입력·출력 Guard | 8 | 500~2,000 | 64~512 |

**결과가 매번 3개이고 정상 완료하며 Guard 검사 한 단계가 내부 LLM 1회인 경우** 검색 1회당 총 12회, 시연 3회당 총 36회다. NeMo가 검사 한 단계에서 여러 번 호출한다면 이 계산보다 증가한다. 로컬 Fixed/Dynamic Guard 점수 계산 자체에는 LLM 토큰 비용이 없다.

| 시연 구성 | 검색 1회 비용 | 검색 3회 비용 |
|---|---:|---:|
| 화면02~04 분류·등록·안내 | $0 | $0 |
| 검색문 생성 | $0.00228~$0.00812 | $0.00684~$0.02436 |
| 결과 3개 설명 생성 | $0.01248~$0.04572 | $0.03744~$0.13716 |
| 입력·출력 Guard 8단계 | $0.01312~$0.07296 | $0.03936~$0.21888 |
| **LLM 총합** | **$0.02788~$0.12680** | **$0.08364~$0.38040** |

따라서 계획용으로 **검색 1회 약 $0.03~$0.13, 3회 약 $0.09~$0.39**로 표현한다. 최초 LLM 사건 정리를 포함했던 45회 예시는 이번 선택한 흐름에 적용하지 않는다.

참고 산식: 검색 1회 입력 총 6,900~25,000 / 출력 총 1,408~7,680토큰, 3회 입력 20,700~75,000 / 출력 4,224~23,040토큰이다.

이 범위는 최대 청구액 보장이 아니다. 현재 생성 출력 한도는 호출당 2,048토큰이다. 생성 4회가 전부 2,048토큰을 쓰고 Guard 8회가 각각 512토큰을 쓰며 입력을 위 상단 값으로 잡는 **별도 시나리오**는 3회 **$0.51864**다. Guard 512토큰은 예약 추정값이며 원격 출력 상한이 아니므로 이 값 역시 절대 상한이 아니다. 실제 첫 호출의 전체 usage·NeMo 내부 호출 수로 범위를 갱신한다.

할인·Fast/Ultrafast·지역 처리·중계 수수료·재시도·실패 후 추가 실행·네이버/인프라 요금은 위 기본 예시에 포함하지 않았다. 현재 검색은 네이버 API **검색 1회당 2건, 3회당 6건**이며 OpenAI 내장 web search 도구 호출 요금을 넣은 구조가 아니다. 외부 검색 제공자의 쿼터·적용 요금은 별도 확인한다.

### 현재 설정과 계산 가정을 구분

- 소스의 생성/Guard 모델·단가 기본값은 여전히 `gpt-4o-mini` 기준이다. 이 문서를 작성하며 6.1로 바꾸지 않았다. 모델 이름만 6.1로 바꾸고 mini 단가를 유지하면 장부가 실제 요금을 과소 계산한다.
- 6.1 Standard 단가를 사용하는 장부의 환산 값은 **입력 $0.002 / 출력 $0.010, 각각 1,000토큰당**이다. 생성과 실제 NeMo Guard 모델을 따로 대조한다. Java의 Guard 비용 모델 이름만 바꿔도 NeMo 실행 모델이 바뀌지는 않는다.
- 현재 예산 기본값은 월 **$2**, 일 **$0.50**, 세션 **$0.12**다. P03은 사용자별 `search:{username}` 비용 세션을 재사용하므로 서로 다른 검색 요청 3개도 같은 세션에 누적된다. 이 예시에서는 1회 상단도 $0.12를 넘으며, 3회 시연이 중간 차단될 수 있다. 예약액 때문에 실사용 누적보다 먼저 거절될 수도 있다.
- 3회 시연 성공 여부 확인과 의도적인 예산 차단 시험을 분리한다. **먼저 정상 1건의 실측을 본 뒤** 2·3회 진행 예산을 결정한다. 이번에는 $0.12/$0.50를 변경하지 않았다. 단가를 부풀려 차단 시험을 하지 않는다.
- 학원 지원액 $20 중 현재 Java 버전 목표 $8~$10 이내, 나머지는 Python 버전용이라는 전체 지출 계획은 별도 관리한다. 메모리 장부는 재시작·다른 도구 지출까지 누적하는 공급자 원장이 아니다.

- [ ] **B04 · LLM 미호출 증명:** 화면02~04만 수행해 생성/Guard 외부 요청 수가 0인지 모의 수신기로 확인한다. 화면 성공이나 과금 화면의 반영 지연만으로 $0이라고 판정하지 않는다.

### C. 개인정보와 외부 전송 — 합성 데이터로

- [ ] **C01 · 송신 허용 필드:** 가상 이름·전화번호·상세 주소·독특한 사건 문장·자유 검색 목적을 표시한 합성 사건으로 P03/Guard 송신 본문을 모의 수신기에서 검사한다. 원문/식별자는 빠지고 분야·분쟁 유형·광역 지역만 남는지 확인한다. 증거에는 실데이터·키를 저장하지 않는다.
- [ ] **C02 · 결과 정제:** 외부 제목/요약의 HTML·전화번호·개인정보 정제와 악성 명령 삽입을 확인한다. 설명 모델이 검색 문서의 명령을 따르거나 다른 사건 정보를 재현하지 않는지 확인한다.
- [ ] **C03 · 조회/다운로드 권한:** 다른 사용자·미인증 사용자의 문의/검색 결과/파일 접근을 확인한다. 기존 공개 조회 경로와 개발용 설정의 한계를 기록하고, 실개인정보를 넣기 전에 허용 범위를 정한다.
- [ ] **C04 · 보관/표시:** 화면·응답·로그·내보내기에서 필요한 마스킹, DB 보관/삭제 범위와 실험 데이터 정리를 확인한다. DB 저장만으로 외부 전송·노출 점검을 완료 처리하지 않는다.

### D. 실제 검색과 설명 품질 — 첫 1건 후 확장

- [ ] **D01 · 최소 정상 1건:** 결과 상한을 일시적으로 1개로 제한한 실험 설정에서 검색문→네이버 두 검색→DB 저장→설명→조회까지 확인한다. 1개 기준 비용은 본문의 3개 기준보다 작지만 실제 usage로 기록한다. 검증 후 원래 3개 설정을 복원한다.
- [ ] **D02 · 조건 반영:** 사건 분야·분쟁 유형·서울/부산 등 다른 광역 지역·선호 조건이 검색문에 의미 있게 반영되는지 확인한다. 저장되는 자유 검색 목적을 LLM이 반영한다고 잘못 표시하지 않는다.
- [ ] **D03 · 변협 출처:** 네이버 색인에서 실제 변협 공개 페이지를 찾는지 확인하고 최종 URL·출처 배지를 대조한다. 비슷한 도메인/제목은 변협으로 표시하지 않으며, 공식 결과 0개일 때 일반 결과와 한계를 표시한다.
- [ ] **D04 · 결과 3개:** 중복 URL 제거·최대 3개·공식/일반 혼합을 확인한다. 프로필별 의미 있는 URL ID는 보존하고 홈페이지/기사/광고만 나오는지 실제 원문으로 확인한다. 자격·최신성·광고 여부는 검색 요약만으로 확정하지 않는다.
- [ ] **D05 · 설명 근거:** 각 설명이 저장된 제목·요약과 조건의 관련성에 근거하는지 확인한다. 이름·경력·승소율·비용·추천 순위·새 URL을 지어내지 않으며 부족하면 원문 확인 필요로 표시한다.
- [ ] **D06 · 3회 시연:** 첫 1건의 비용/품질이 적절하면 가상 사건 3개를 서로 다른 C06 검색 요청 ID로 실행하고 결과·설명·지연·비용을 각각 기록한다. 동일 완료 ID를 세 번 누르는 것은 세 번의 새 검색 시험이 아니다.

### E. 오류·재실행·브라우저 복귀 — 장애는 우선 모의 검증

- [ ] **E01 · 중복 실행:** 같은 요청을 동시에 클릭하거나 실행 중/완료 후 POST를 다시 보내도 검색/생성 호출이 추가되지 않는지 호출 수와 함께 대조한다. 새 요청 ID는 새 비용이며 동일 사용자 비용 세션은 유지되는지 확인한다.
- [ ] **E02 · 부분 완료 재시도:** 설명 1개만 실패한 PARTIAL에서 결과/ID/출처 경고가 보존되고, 명시적 재시도는 누락 설명과 해당 Guard만 호출하는지 확인한다. 검색문/네이버 검색/성공 설명을 다시 유료 생성하지 않는지 확인한다.
- [ ] **E03 · 검색 0개/부분 장애:** 양쪽 정상 0개는 NO_RESULTS·설명 호출 0회, 한쪽 실패+다른 쪽 결과는 경고와 결과 유지, 양쪽 실패 또는 실패+다른 쪽 빈 결과는 실패로 표시되는지 확인한다.
- [ ] **E04 · LLM/Guard 장애:** 잘못된 JSON·빈 응답·잘린 출력·429·5xx·timeout·입력/출력 Guard 차단을 구분한다. 결과를 꾸며내지 않고 이미 발생한 단계 비용과 상태를 보존하는지 확인한다.
- [ ] **E05 · 인증/설정/ID 오류:** 키 미설정·JWT 만료·다른 사용자 실행·없는 요청 ID·잘못된 요청 필드를 확인한다. 자동 반복 POST나 Guard 우회로 이어지지 않는지 확인한다.
- [ ] **E06 · 화면 종료/복귀:** P03 실행 중 이동·탭 종료 후 서버 작업이 계속되는 특성을 확인하고 같은 ID로 복귀 시 기존 작업을 조회하는지 확인한다. GET 폴링·새로고침만으로 새 LLM 호출이 발생하지 않아야 한다.
- [ ] **E07 · 작업 생명주기:** 전체 deadline·대기열 초과·서버 재시작으로 미완료된 작업의 표시와 수동 재개 기준을 확인한다. 재시작 후 자동 유료 재실행이 없어야 한다.

### F. 비용·예산·관측 대조

- [ ] **F01 · 실제 호출 수/토큰:** 검색문 1·설명 N·전후 Guard 2×(1+N)를 실제 공급자 호출과 대조한다. Guard 내부 다중 호출, reasoning 포함 출력·보고 모델·usage 유무를 기록하고 비용 범위를 다시 계산한다.
- [ ] **F02 · 공급자/장부 대사:** 각 단계의 보고 토큰×해당 모델 단가가 C16 actual/stage 비용과 맞는지 확인한다. 공급자 집계 지연·공유 프로젝트의 다른 사용량을 고려한다. 미확인 usage를 실제 0으로 처리하지 않는다.
- [ ] **F03 · 예약 종료/예외 정산:** 정상·출력 차단·발송 후 오류에서 이미 사용한 비용이 유지되고, 미발송 예약만 해제되며, 최종 진행 예약이 누락 없이 종료되는지 확인한다. 사용량 미확인은 추정 정산으로 구분한다.
- [ ] **F04 · 경합/날짜/재시작:** 완료·오류 콜백 경합의 단 한 번 정산, 동시 예약, 자정 경과 시 예약일 귀속을 모의 재현한다. 재시작으로 메모리 장부가 초기화되는 점을 실험 기록/공급자 사용량과 함께 관리한다.
- [ ] **F05 · 작은 예산 차단:** 별도 비과금 차단 프로필과 P03 모의 경로에서 호출 전 비용 거절·미실행·예약 정리를 확인한다. 정상 단가를 유지한 채 예산만 작게 하고, 정상 검색 품질 실험과 설정을 분리한다.
- [ ] **F06 · 사용자 누적/3회 한도:** 다른 검색 요청 ID 3개도 `search:{username}`에 누적되는지 확인한다. 첫 실측 후 세션 $0.12/일 $0.50에서 다음 시연의 예약을 수용할 수 있는지 판단한다. Java 전체 목표 $8~$10과 Python용 잔액도 공급자 기준으로 기록한다.
- [ ] **F07 · 운영자 해석:** 화면13 Fixed/Dynamic 두 흐름, 비용 단계와 차단 사유를 실제 실험과 대조한다. 관측 없음 `—`와 실제 0, 정산/예약, 동기 Chat 평균 시간과 P03/SSE 지연을 혼동하지 않게 확인한다.

### G. 별도 Chat/SSE 회귀 — 이번 P03 3회 비용에 미포함

- [ ] **G01 · 정상 Chat/SSE:** 필요 시 각각 최소 1건으로 실제 모델·Guard·usage·출력 마스킹·종료 이벤트를 확인한다. P03 시연의 선행 유료 호출로 강제하지 않는다.
- [ ] **G02 · 연결 종료:** 발송 전/후 브라우저 취소와 공급자 실제 종료 시점, 늦게 도착한 usage·출력 노출·추정 정산을 확인한다. 로컬 취소가 공급자 청구 즉시 취소를 뜻하지 않는다.
- [ ] **G03 · 오류/중복 종료:** timeout·외부 오류·Guard 출력 차단·완료/오류 경합에서 실제/추정 비용과 정확히 한 번 종료 상태를 대조한다. 로컬 모의 확인과 공급자 확인을 구분한다.

## 5. 권장 실행 순서와 기록 양식

**A 준비 → B/C 비과금 재현 → D01 결과 1개 정상 → F 비용 대사 → D02~D06 결과 3개·시연 3회 → E/F 장애 모의 보완 → 필요 시 G 별도 SSE** 순서다. 실패 원인을 확인하기 전 반복 유료 재시도를 하지 않는다. 현재 문서의 미완료 체크는 실제 실행 후 증거·날짜를 붙여 변경한다.
