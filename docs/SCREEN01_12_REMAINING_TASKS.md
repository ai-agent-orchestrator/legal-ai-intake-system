# 화면01~12 검수 후 남은 작업

최초 정리: 2026-10-22. 완료 상태 갱신: 2026-10-23. 화면별 통합 검수와 이후 P03·SSE 수정 기록을 대조했다. 접근 제어, DTO, Incident 처리의 현재 소스도 확인했다. 이번 작업은 남은 항목 정리이며, 전체 빌드·브라우저·실제 API 시험을 새로 실행한 결과가 아니다. 아래 미완료 표시는 구현 부족, 실사용 미검증, 확장 범위를 구분한다.

## 1. 먼저 수정할 항목

우선순위 P1은 접근·정보 노출 문제, P2는 서버 검증·데이터 정합성 문제다. 프런트 버튼 잠금이나 마스킹 표시만으로 서버 문제의 완료 체크를 하지 않는다.

- [x] **P1-01 · 문의 조회·변경 권한 — 화면04~08 / C03~C11·P02~P05·C21**
  - 완료: JWT 필수 접수, 의뢰인 본인 문의/배정 LAWYER/ADMIN 범위, ADMIN 담당자 배정·해제, 내부 메모의 의뢰인 JSON 제외, JWT 메모 작성자와 React 권한·로그아웃 처리를 적용했다. 무소유 기존 문의는 ADMIN만 접근한다.
  - 검증: 마지막 실행 기록에서 백엔드210개, 문의142개·운영자35개, production 빌드, 실제 브라우저14개 검사 통과. 이번 문서 정리는 2026-10-23이며 검사 재실행이 아니다.
  - [상세 계약·DB 변경·증거](SCREEN04_08_ACCESS_CONTROL_REVIEW.md). 실제 MySQL 이전, 운영 계정, 영구 멱등성은 별도 미완료다.

- [ ] **P1-02 · 운영자 업무 API 관리자 인가 — 화면09~12 / C12~C15, C17~C20**
  - 현재: C16·보조 guardtimeseries는 ADMIN Basic으로 보호되고 운영자 업무 API 8개는 아직 공개다.
  - 할 일: 업무 API의 ADMIN 인가와 프런트 로그인 세션·헤더 전달을 함께 연결한다. C16의 별도 Basic 인증은 구분한다.
  - 완료 기준: 익명 401, 일반 사용자 403, ADMIN 정상 조회/변경 및 만료 후 복구 확인.

- [ ] **P1-03 · 위험 이력 응답의 원문 제거/마스킹 — 화면12 / C17**
  - 현재: 화면에는 원문을 렌더링하지 않지만 `AgentRiskHistoryResponse.userInput`에 원문이 담긴다. 화면13 후속 점수 필드 추가도 이 문제를 해소하지 않았다.
  - 할 일: 운영상 필요한 최소 필드를 정하고 원문 제외 또는 서버 마스킹을 적용한다.
  - 완료 기준: 가상 개인정보 표식이 UI뿐 아니라 네트워크 JSON에서도 원문으로 나오지 않음.

- [ ] **P2-01 · 간단 안내 서버 입력 검증 — 화면04 / C04**
  - 현재: `MinimalLegalIntakeRequest`의 필수·길이 등 Bean Validation 및 Controller의 `@Valid`가 없다.
  - 할 일: 필수/선택 필드, 최대 길이, 배열·항목 상한, 지원 코드 계약을 확정해 서버에 적용한다.
  - 완료 기준: 직접 API 호출의 빈 필수 값·초과 길이·잘못된 값은 400, 유효한 저장 문의 기반 안내는 정상 처리.

- [ ] **P2-02 · 수동 검색 결과 서버 검증 — 화면05 / C08**
  - 현재: 프런트는 위험 URL과 비양수 순서를 막지만 DTO에는 URL 길이·공백 검사만 있고 `displayOrder` 양수 제약이 없다. 이전 직접 API 검수에서 위험 프로토콜과 음수 순서가 저장됐다.
  - 할 일: HTTP(S), 호스트·사용자정보 없는 URL, 제어문자 등 URI 정책과 표시 순서의 양수 검증을 서버에도 적용한다.
  - 완료 기준: 프런트를 거치지 않는 잘못된 요청도 400 및 DB 미저장. 정상 URL과 순서 생략 시 자동 순서 계약 유지.

- [ ] **P2-03 · 문의 접수의 중복 저장 방지 — 화면03 / C03**
  - 현재: 중복 클릭 방지는 있으나 응답 유실 후 재접수의 서버 멱등 계약은 없다.
  - 할 일: 요청 식별자와 같은 요청/다른 본문 처리 규칙을 정하고 React와 서버에 연결한다.
  - 완료 기준: 최초 저장 후 응답 유실·동일 요청 재전송·동시 요청에서도 문의는 한 건이며 같은 ID를 확인할 수 있음.

- [ ] **P2-04 · 상태·메모의 동시 수정/중복 쓰기 — 화면07~08 / C10·C11**
  - 현재: 프런트 잠금과 불확실한 저장 후 재조회는 있으나 기대 버전·이전 상태 계약과 모든 쓰기의 영구 멱등 보장은 없다.
  - 할 일: 복수 담당자의 상태 변경 충돌, 동일 메모 재전송 처리 규칙을 정한다.
  - 완료 기준: 경쟁 상태 변경은 충돌을 명확히 알리고, 같은 메모 요청의 중복 저장을 방지함.

- [ ] **P2-05 · Incident 상태 전이·중복 처리 — 화면12 / C19·C20**
  - 현재: 서버의 `acknowledge()`는 상태를 무조건 바꿔 RESOLVED→ACKNOWLEDGED 역행이 가능하다. 이전 브라우저 전송 시험에서는 같은 PATCH가 두 번 도달했다. 재전송 주체는 확정되지 않았다.
  - 할 일: 허용 전이, 같은 상태 재요청의 무해성, 동시 ack/resolve 충돌을 서버에서 처리한다. 중복 도달 원인도 분리 확인한다.
  - 완료 기준: 해결된 Incident가 다시 확인됨으로 돌아가지 않음. 잘못된 전이는 정한 409 계약으로 처리하고 재전송·경합 시 최종 상태가 일관됨.

- [ ] **P2-06 · 없는 Incident의 오류 계약 — 화면12 / C19·C20**
  - 현재: 없는 ID를 `IllegalArgumentException`으로 던지며 이전 실제 응답은 404 대신 500이었다. 현재 예외 처리에도 해당 404 매핑이 없다.
  - 할 일: 대상 없음 전용 예외 또는 상태 예외를 사용한다.
  - 완료 기준: 없는 숫자 ID는 404, 잘못된 ID 형식은 400, 기존 데이터 변경 없음.

## 2. 구현은 있으나 실사용 확인이 남은 항목

이 절은 미개발 목록이 아니다. 로컬 모의 제공자 검증과 실제 공급자·실행 환경 확인을 구분한다. 키 값은 문서·채팅·증거에 기록하지 않는다.

- [ ] **V01 · 실제 호출 준비**: 학원 초대 수락·프로젝트·모델 사용 권한·잔액, 서버의 생성/Guard/네이버 설정 여부와 실사용 모델·단가·출력 상한 확인. 실행 서버 C16의 예산 적용값도 대조한다. 현재 설정 완료 여부를 이번 정리에서 다시 확인한 것은 아니다.
- [ ] **V02 · 화면05 P03 최소 정상 1건**: 결과 1개로 검색문 생성→네이버 변협 도메인 대상 검색+일반 웹 검색→병합·저장→설명 생성→같은 요청 ID 재조회까지 확인. 변협 전용 API/직접 크롤링으로 설명하지 않는다.
- [ ] **V03 · 검색 품질·설명 근거**: 실제 `site:klaw.or.kr` 적중률, 지역·법률 분야 관련성, 원문 URL·프로필 여부, 중복 제거·부분 장애 안내, 설명의 근거 일치 확인. 조건과 무관한 페이지나 생성된 경력·추천 근거를 정상 추천으로 판정하지 않는다.
- [ ] **V04 · 실제 비용 대조와 3회 시연**: 생성·입출력 Guard 호출 수/usage, actual·estimated·accounted·reserved 및 공급자 사용량 대조. 최소 정상 1건 후 결과 수와 실행 횟수를 늘린다. 가격 추정표는 실측 결과가 아니다.
- [ ] **V05 · SSE 실공급자 확인(별도 SSE 시연 시)**: 정상·중단의 terminal 이벤트, 마스킹, usage 유무와 추정 정산을 확인한다. 로컬 HTTP 취소와 공급자의 즉시 청구 중단을 같은 것으로 판정하지 않는다. P03 시연의 필수 선행 유료 호출은 아니다.
- [ ] **V06 · 최근 변경의 화면05 브라우저 회귀**: 변협/일반 웹 혼합 검색과 출처 경고 후속 변경은 자동 검사·렌더 검증이 있고, 기존 51개 브라우저 시나리오를 그 변경 후 전부 재실행한 기록은 아니다. 출처·경고·부분 완료·복귀를 데스크톱/모바일에서 추가 확인한다.
- [ ] **V07 · 수정 후 최종 통합 회귀·배포 환경**: 위 서버 계약을 바꾼 뒤 화면01→05, 화면06→상세/메모, 화면09→12 연결과 인증 실패·입력·로딩·빈 결과·오류 복구를 재확인한다. 실제 배포의 정적 파일/프록시/CORS·보안 설정, 운영 계정과 실제 사용 브라우저도 확인한다.

## 3. 서비스 확대 또는 추가 기능 범위

아래는 기존 연결 실패와 구분한다. 로컬 단독 시연 전에 모두 신규 개발해야 한다는 의미는 아니며 실제 사용 범위에 맞춰 우선순위를 정한다.

- [ ] **영구 변경 감사 기록**: 화면07~08의 상태 변경 이력, 실제 작성자·수정일 계약 및 저장. 현재 임시 화면 이력을 영구 감사 이력으로 설명하지 않는다.
- [ ] **전체 데이터 검색/페이지네이션**: 화면06 필터·통계는 최근 최대50건 기준이다. 전체 DB 검색·전체 통계가 필요하면 서버 계약을 추가한다. C17 조건 조회의 결과 상한·페이지네이션도 정한다.
- [ ] **파일 업로드 UI와 추가 메뉴**: 다운로드 API 연결과 별개로 업로드 UI, 자료 준비 완료 저장, 변호사 홈·자료 관리·내 정보 등의 필요 범위를 확정한다.
- [ ] **DB 영속성·스키마 이행**: H2 메모리 초기화와 운영 DB를 구분한다. P03 및 담당 변호사·메모 작성자 컬럼 변경의 실제 MySQL 이행·재시작·복구·장기 운영을 검증한다.
- [ ] **비용 원장 영속성·청구 대사**: 현재 프로세스 메모리 장부를 재시작·다중 인스턴스까지 보존하는 원장, 추정액 사후 보정 및 외부 사용량 대사로 확장한다.
- [ ] **서버 사용량/부하 통제**: Chat/SSE 사용자별 요청 빈도·동시 실행·중복 처리와 세션 변경을 통한 누적 한도 우회 가능성을 다룬다. P03 단일 서버 실행기를 분산 환경에 그대로 적용하지 않는다.
- [ ] **확대 품질 검증**: 모든 모바일 기기·브라우저, 접근성 전체, 대량 데이터·장기 부하·장애 복구 검증. 기존 모바일390px 검수 통과를 모든 기기 통과로 확대하지 않는다.

## 4. 남은 개발에서 제외할 완료 사항

- [x] 화면01~12의 기본 API·요청/응답·ID 전달·React 라우팅·공통 구성 검수 기록이 있다.
- [x] 화면01~04 브라우저50개, 화면05~08 브라우저51개, 화면09~12 브라우저57개 및 각 회차 빌드·자동 검사 기록이 있다. 회차 수치를 최신 전체 재검수나 상호 독립 테스트로 합산하지 않는다.
- [x] 기존 화면10 모바일 가로 넘침, 잘못된 운영 요약 응답의 흰 화면, P03 빈 JSON 기본값 문제는 수정됐다.
- [x] P03 실행·검색문/설명 생성·결과 저장과 로컬 모의 제공자 검증은 구현됐다. 초기 문서의 ‘P03 개발 전’ 상태는 현재 미완료 항목이 아니다.
- [x] 변협 도메인 대상 검색과 일반 웹 검색 병합·출처 판정·부분 장애 경고가 구현됐다. 실제 검색 품질은 V03에 남는다.
- [x] SSE usage 구분, 예약의 최초 종료 처리, 중단·오류 정산, 날짜 귀속, 출력 마스킹이 구현되고 로컬 모의·동시성 검증됐다. 실제 청구 확인과 원장 영속성은 별도다.
- [x] 단가 단위 오류·사건 본문100자 통일·기본 예산 설정·비과금 작은 예산 차단 검사가 반영됐다. 실제 실행 모델/설정 적용 및 공급자 대사는 별도다.

## 5. 권장 순서

실제 데이터나 외부 접속을 허용하기 전에는 P1 접근·노출 문제를 먼저 처리한다. 제품 수정은 P1→P2 서버 계약→통합 회귀 순서다. 로컬 가상 데이터로 제한한 P03 실험은 V01 준비→V02 결과1개→V04 비용 대조→V03 품질·3회 시연 순서로 진행한다. 추가 기능과 영속 운영 개발은 별도 범위로 정한다.
