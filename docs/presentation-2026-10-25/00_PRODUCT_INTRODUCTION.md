## Problem → Solution

### 01 시장 | 초기 문의가 상담으로 이어지도록
문제: 소규모 사무소에서 문의를 구조화하지 못하면 상담 전환 손실이 생길 수 있습니다.
해결: 사건 유형·보유 자료·원하는 다음 단계로 문의를 정리합니다.
### 02 UX | 법률 용어를 몰라도 시작하도록
문제: 처음부터 긴 주관식으로 사건을 설명하기 어렵습니다.
해결: 선택형 입력과 체크리스트를 중심으로 안내문을 구성합니다.
### 03 기술 | 일관된 입력과 분류
문제: 자유대화는 입력이 길어지고 구조가 불안정해질 수 있습니다.
해결: Legal Intake Form과 Spring Java의 규칙·템플릿으로 분류를 안정화합니다.

### 04 보안 | 호출 전후의 위험 통제
문제: 위험 요청·반복 공격·비용 폭주·개인정보 재출력 위험이 있습니다.
해결: Fixed Guard·Dynamic Guard·Cost Control·Privacy Output Guard를 적용합니다.
### 05 운영 | 차단 이유와 문의 흐름 확인
문제: 기록과 지표가 없으면 운영자가 문제를 파악하기 어렵습니다.

### 06 확장 | 다음 단계는 분리해서 준비
문제: 심층 문서 검색·전달 요약·후속 연락 자동화는 추가 설계가 필요합니다.
계획: 12월 RAG·Python actions.py·Vector DB·카카오톡/이메일 연동을 검토합니다.

## 회고와 다음 개발 방향
구현한 흐름을 더 깊이 이해하고, 검증한 보안·비용 통제 위에서 확장하겠습니다.
### 01 백엔드 흐름을 끝까지 이해하기
Top–Middle–Bottom을 더 리뷰하고 싶습니다.
API → Controller → Service·Policy → DB·외부 호출 → 응답·Metric을 추적합니다.
정상·실패·차단 경로를 직접 설명하는 것이 목표입니다.
### 02 Python Action으로 보안 확장
NeMo actions.py에 정책 검사·마스킹을 연결해보고 싶습니다.
작은 검사 Action부터 시작하고, 오류·시간 초과·권한을 검증합니다.
Spring의 기존 차단·비용 정책과 연결합니다. 향후 개발 계획입니다.
### 03 공식 자료부터 RAG 증강
공식 절차·양식·FAQ를 작은 검색 범위로 시작합니다.
검색 근거·출처·갱신일을 제시하고, 근거가 부족하면 답변을 제한합니다.
이후 권한별 내부 문서와 검색 내용의 주입 공격 검증으로 확장합니다.
### 04 이번 개발에서 얻은 기준
기능 연결뿐 아니라 실패·비용·운영까지 설명하고 검증하는 것이 중요했습니다.
이해 강화 → Python Action → 소규모 RAG 순서로 발전시키겠습니다.
새 기능에도 정상·실패·차단 회귀 검증을 유지합니다.
